VPC の構成要素 5.1.1

部品要点
CIDRVPC は /16〜/28。後からセカンダリ CIDR を追加可能。サブネットは AZ に属し、先頭 4 つと最後の 1 つ、計 5 アドレスが予約（ネットワーク、VPC ルーター、DNS、将来用、ブロードキャスト）。VPC ピアリングや TGW で接続する VPC は CIDR が重複してはならない
ルートテーブルサブネットに 1 つ関連付け（未指定ならメインルートテーブル）。最長一致で宛先を選ぶ。VPC 内の local ルートは削除できない
インターネットゲートウェイVPC に 1 つ。インスタンス側にパブリック IPv4（または Elastic IP）が必要。IPv6 の双方向通信も担う
NAT ゲートウェイプライベートサブネットからの IPv4 外向き通信。パブリック NAT はパブリックサブネットに置き EIP を付ける（リージョナル NAT ゲートウェイはパブリックサブネット不要）。時間料金＋処理データ量の料金。宛先ごとの同時接続数に上限があり、枯渇は ErrorPortAllocation メトリクスで分かる。プライベート NAT は重複 CIDR 間の接続用
NAT インスタンス旧方式。使う場合は EC2 の送信元／送信先チェックを無効化する必要がある
Egress-Only インターネットゲートウェイIPv6 専用の外向き通信（外からの開始は拒否、ステートフル）。IPv6 には NAT がないため、プライベートにしたい IPv6 サブネットはこれを使う
Elastic IP固定のパブリック IPv4。2024 年 2 月以降、パブリック IPv4 アドレスは使用中でも時間料金がかかる。未使用の EIP は解放
DNS 属性enableDnsSupport（Amazon 提供 DNS の利用）と enableDnsHostnames（DNS ホスト名の付与）。プライベートホストゾーンとインターフェイス型エンドポイントのプライベート DNS には両方 true が必要
VPC ブロックパブリックアクセスアカウント・リージョン単位で VPC の IGW 経由の通信を一括遮断（例外設定可）
IPAM組織全体の IP アドレス空間をプールで計画・割り当て・監視。VPC 作成時に重複しない CIDR を自動割り当て、重複や未使用を検出

セキュリティグループとネットワーク ACL 5.1.1 5.3.1

項目セキュリティグループ（SG）ネットワーク ACL（NACL）
適用単位ENI（インスタンス、ALB、RDS、エンドポイントなど）サブネット
状態ステートフル：許可した通信の戻りは自動で許可ステートレス：行きと戻りの両方にルールが必要
ルール許可のみ（拒否ルールは書けない）許可と拒否。番号の小さい順に評価し、最初に一致したもので決定。最後は * の拒否
参照送信元に他の SG を指定できる（例：ALB の SG からのみ許可）CIDR のみ
既定新規 SG：インバウンドなし、アウトバウンド全許可既定 NACL：全許可。カスタム NACL：作成時は全拒否
得意なことアプリ単位の細かな許可特定 IP の明示的なブロック、サブネット単位の大まかな防御
ひっかけ注意
  • 「SG のアウトバウンドでエフェメラルポートを許可」は不要です（ステートフルなので戻りは自動）。NACL のアウトバウンドに SSH の 22 番を足す選択肢も誤り（戻りの宛先は 22 ではない）。
  • NAT ゲートウェイや ALB を経由する場合も、それぞれのサブネットの NACL で戻りのエフェメラルポートが必要です。
  • 特定の攻撃元 IP を遮断したい → SG では拒否を書けないので NACL の拒否ルール（許可ルールより小さい番号で）。Web アプリなら WAF の IP セットでも可。

VPC ピアリング

2 つの VPC を 1 対 1 でつなぎます。同一アカウント・別アカウント・別リージョンいずれも可能で、通信は AWS ネットワーク内を通ります。推移的ルーティングは不可（A–B、B–C がピアでも A から C へは行けない）、CIDR の重複は不可、相手側の IGW・NAT・VPN を経由する「エッジ間ルーティング」も不可です。

VPC-A（10.0.0.0/16）のルートテーブルターゲット
10.0.0.0/16local（自動・削除不可）
192.168.0.0/16（VPC-B の CIDR）pcx-11111（ピアリング接続）

VPC-B 側にも 10.0.0.0/16 → pcx-11111 のルートが必要です。さらに両側の SG で相手の CIDR（同一リージョンなら相手の SG ID も可）を許可します。ピアリング接続は作成後に相手側で承諾しないと有効になりません（演習 PDF 問題 14）。

Transit Gateway・VPN・ハイブリッド接続 5.1.2 5.3.4

接続方式要点トラブルの典型
Site-to-Site VPN仮想プライベートゲートウェイ（VGW）または TGW とカスタマーゲートウェイ間の IPsec。トンネルは 2 本（冗長化のため両方を設定）。静的ルーティングか BGP の動的ルーティング。1 トンネルの帯域には上限がある（TGW と ECMP で複数 VPN を束ねて拡張）トンネル DOWN（IKE/IPsec パラメータの不一致、オンプレ側ファイアウォールで UDP 500／4500 が閉じている、DPD タイムアウト）。トンネルは UP なのに通信できない → VPC のルートテーブルでルート伝播が無効、SG／NACL、オンプレ側のルート。メトリクスは TunnelState
Client VPN個々の PC から VPC へリモートアクセス（OpenVPN 互換）。認証は相互証明書・Active Directory・SAML。承認ルールでアクセスできる宛先を、ルートテーブルで経路を指定。スプリットトンネルで VPC 宛て以外はローカルから出す接続できても到達しない → 承認ルールとルートの不足、関連付けたサブネットの SG。クライアント CIDR が VPC と重複
Direct Connect（参考）専用線。プライベート VIF（VPC）、パブリック VIF（AWS のパブリックサービス）、トランジット VIF（TGW）。既定では暗号化されない（MACsec か VPN を重ねる）。バックアップに VPN を併用BGP セッションのダウン、経路広告の誤り、VPN との経路優先度
Transit Gatewayリージョン内のハブ。TGW ピアリングでリージョン間接続。ステートフルな検査アプライアンスを経由するならアプライアンスモードで非対称ルーティングを防ぐアタッチメントの関連付け・伝播の漏れ、VPC 側サブネットのルートテーブルに TGW 宛てルートがない、ブラックホールルート
試験の着眼点：ハイブリッドの名前解決

VPN でつながったのにオンプレミスから example.internal が引けない → ネットワークではなく DNS の問題です。Route 53 Resolver のインバウンドエンドポイントとオンプレ DNS の条件付きフォワーダーを設定します（Resolver の節）。

ネットワークアーキテクチャのコスト最適化 5.1.4

コストの発生源削減策
NAT ゲートウェイのデータ処理料金S3・DynamoDB への通信はゲートウェイ型エンドポイントへ（無料）。ECR・CloudWatch など頻繁に使うサービスはインターフェイス型エンドポイントと NAT の料金を比較。開発環境は NAT を置かない設計も検討
AZ 間のデータ転送同じ AZ 内で完結させる（AZ ごとの NAT、同一 AZ のエンドポイント）。NLB のクロスゾーン負荷分散を有効にすると AZ 間転送が発生
インターネットへのデータ転送（アウト）CloudFront を前段に置く（オリジンから CloudFront への転送は無料で、CloudFront からの配信単価の方が有利な場合が多い）。圧縮、キャッシュヒット率の向上
パブリック IPv4 アドレス使っていない Elastic IP を解放、パブリック IP が不要なインスタンスはプライベートに、IPv6 の活用
Transit Gatewayアタッチメントの時間料金＋処理データ料金。少数の VPC 間の大容量通信なら VPC ピアリング（時間料金なし）の方が安い場合がある
リージョン間転送レプリケーションの対象を必要なものに絞る、圧縮
試験の着眼点

「プライベートサブネットのインスタンスが S3 と大量にやり取りしていて NAT ゲートウェイの料金が高い」→ S3 のゲートウェイ型 VPC エンドポイントを作り、プライベートサブネットのルートテーブルに関連付ける、が定番の正解です。料金の内訳は Cost Explorer の使用タイプ（NatGateway-Bytes、DataTransfer-Regional-Bytes など）で確認します。
