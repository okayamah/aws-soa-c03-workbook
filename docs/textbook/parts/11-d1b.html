コンピューティングの最適化 1.3.1

タスク 1.3 は旧 SOA-C02 の「コストとパフォーマンスの最適化」分野を引き継いでいます。運用者に求められるのは、メトリクスとツールの推奨事項から過剰／過小なリソースを見つけ、安全に変更することです。中心となるツールは AWS Compute Optimizer です。

ツール何を推奨するか押さえる要点
AWS Compute OptimizerEC2、Auto Scaling グループ、EBS ボリューム、Lambda 関数、ECS on Fargate、RDS／Aurora などのサイズ適正化（タイプ・サイズ・メモリ量）利用前にオプトインが必要（Organizations の管理アカウントから一括も可）。既定で過去 14 日の CloudWatch メトリクスを分析し、検出結果は「過剰プロビジョニング／過小プロビジョニング／最適化済み」。拡張インフラストラクチャメトリクス（有料）で分析期間を 93 日に延長。メモリを考慮させるには CloudWatch エージェントでメモリを送る（または外部監視ツールから取り込み）。
AWS Trusted Advisorコスト最適化・パフォーマンス・セキュリティ・耐障害性・サービスクォータ・運用上の優秀性のチェックアイドル状態の RDS、低使用率 EC2、未関連付けの Elastic IP などを指摘。ただしサイズ適正化の詳細は Compute Optimizer のデータを利用しています。
Cost Optimization Hub組織全体のコスト削減機会（サイズ適正化、Savings Plans、アイドル削除など）を集約・優先順位付け重複を排除した推定削減額で比較できる。
Cost Explorerコストと使用量の可視化・予測、RI／Savings Plans の購入推奨、サイズ適正化推奨原因分析と傾向把握のためのツール。
演習 PDF の論点（問題 1）

EC2・Lambda・EBS の最適化推奨を「直接」得るなら Compute Optimizer。Trusted Advisor も推奨を出しますが内部で Compute Optimizer などのデータを使っており、Cost and Usage Report や Cost Explorer はコストの可視化が主目的です。

インスタンスタイプを変更する手順

  1. 互換性を確認する

    同じアーキテクチャ（x86_64／arm64）か、仮想化タイプ（HVM）、ENA ドライバー・NVMe ドライバーの有無、アタッチできる EBS ボリューム数とネットワークインターフェイス数。

  2. EBS-backed なら停止する

    実行中のままタイプは変えられません。インスタンスストアがルートのインスタンスはタイプ変更できないので、新しいインスタンスへ移行します。

  3. タイプを変更して起動する

    停止中にインスタンスタイプを変更して起動。パブリック IPv4 アドレス（Elastic IP でないもの）は変わります。インスタンスストアのデータは消えます。

  4. Auto Scaling 配下なら起動テンプレートを更新

    個々のインスタンスではなく、起動テンプレートの新バージョンを作り、インスタンスの更新（Instance Refresh）で順次置き換えます。

演習 PDF の論点（問題 2）

t3 から C 系へ変更 → 「停止 → タイプ変更 → 起動」。スナップショットからの起動や AMI からの新規起動は不要な遠回りで、実行中の変更は不可能です。

性能問題を見抜くメトリクス

VolumeQueueLength
処理待ちの I/O 数。高止まりなら IOPS が足りない（プロビジョンド IOPS を増やす、gp3 の IOPS 追加、io2 へ）。
BurstBalance
gp2・st1・sc1 のバーストクレジット残量（%）。0 付近ならベースライン性能まで落ちている。
VolumeReadOps / WriteOps
期間あたりの I/O 回数。期間の秒数で割ると IOPS。
VolumeThroughputPercentage
プロビジョンド IOPS（io1/io2）に対する実績の割合。
VolumeIdleTime
I/O がなかった時間。未使用ボリュームの発見（削除してコスト削減）。
EBSIOBalance% / EBSByteBalance%
インスタンス側の EBS 帯域のバーストクレジット。ボリュームではなくインスタンスの EBS 帯域上限がボトルネックかを判断。

運用操作の要点

Elastic Volumes
タイプ・サイズ・IOPS・スループットをオンラインで変更（デタッチ不要）。同じボリュームの次の変更までは 6 時間待つ。縮小は不可。サイズ拡張後は OS 側でパーティションとファイルシステムの拡張（growpart・xfs_growfs／resize2fs）が必要。
スナップショット
増分バックアップで S3（リージョン単位）に保存。リージョン間コピー可能。スナップショットから作ったボリュームは初回アクセス時にブロックを遅延ロードするため初期性能が低い → 高速スナップショット復元（FSR）を有効化するか、fio／dd で全ブロックを読み込んで初期化。
アーカイブ／ごみ箱
スナップショットアーカイブ層は長期保存を安価に（復元に時間がかかる）。ごみ箱（Recycle Bin）で誤削除したスナップショットや AMI を保持期間内なら復元可能。
Data Lifecycle Manager
タグを付けたボリュームのスナップショットや EBS-backed AMI の作成・保持・リージョン間コピーをポリシーで自動化（AWS Backup との違いは第 2 章）。
暗号化
リージョン単位で「EBS 暗号化をデフォルトにする」を有効化できる。既存の未暗号化ボリュームは直接暗号化できない → スナップショット作成 → 暗号化を指定してコピー → そこからボリューム作成 → 付け替え。
マルチアタッチ
io1/io2 のみ。同じ AZ の最大 16 台の Nitro インスタンスに同時接続。クラスター対応のファイルシステムやアプリ側の排他制御が必要（通常のファイル共有には EFS を使う）。

S3 のパフォーマンス戦略とデータ転送 1.3.3

S3 はプレフィックスごとに 1 秒あたり PUT/COPY/POST/DELETE 3,500 件、GET/HEAD 5,500 件を処理でき、プレフィックスを分ければ並列にスケールします。性能の改善策は「アップロードを速くする」「ダウンロードを速くする」「大量データを移す」「保存コストを下げる」の 4 つに分けて覚えます。

課題手段要点
大きなファイルのアップロードマルチパートアップロード100 MB を超えたら推奨、5 GB を超える単一 PUT は不可なので必須。パート（5 MiB〜5 GiB、最大 10,000 個）を並列送信し、失敗したパートだけ再送できる。未完了のアップロードはパートが残り課金されるため、ライフサイクルルールで「不完全なマルチパートアップロードの中止」を設定。
遠隔地からのアップロードS3 Transfer AccelerationCloudFront のエッジロケーションで受けて AWS のバックボーンで転送。バケット単位で有効化し、バケット名.s3-accelerate.amazonaws.com エンドポイントを使う。バケット名にピリオド不可（DNS 準拠名のみ）。高速化されなかった転送には追加料金がかからない。
大きなファイルのダウンロードバイト範囲の取得（Range GET）範囲を分けて並列に GET。失敗した範囲だけ再取得できる。
高頻度の読み取りCloudFront、または ElastiCache同じオブジェクトを何度も配信するならエッジにキャッシュ。
極めて低いレイテンシーS3 Express One Zone（ディレクトリバケット）単一 AZ で 1 桁ミリ秒。コンピューティングと同じ AZ に置く。
オンプレミスからの大量移行・定期同期AWS DataSyncオンプレミスにエージェントを置き、NFS／SMB／HDFS／オブジェクトストレージから S3・EFS・FSx へ転送。暗号化、整合性検証、スケジュール、帯域制限を自動で扱う。
オンプレミスから継続的にアクセスAWS Storage GatewayS3 File Gateway（NFS／SMB で S3 に保存）、Volume Gateway、Tape Gateway。移行ではなくハイブリッドで使い続けるための仕組み。
演習 PDF の論点（問題 25）

S3 へのアップロード高速化 → Transfer Acceleration。CloudFront はダウンロード配信のキャッシュ、VPC エンドポイントはプライベート接続、Global Accelerator は ALB・NLB・EC2 向けで、いずれも S3 アップロードの高速化策ではありません。

試験の着眼点
  • アクセス頻度が予測できない → Intelligent-Tiering。予測できる（例：30 日後はほぼ参照しない）→ ライフサイクルルール。
  • どのデータがどのくらい読まれているか分からない → S3 Storage Lens やストレージクラス分析で把握してからルールを作る。
  • Standard-IA・One Zone-IA へは、Standard 等に最低 30 日置かないと移行できません。128 KB 未満の小さいオブジェクトは IA に移すとかえって割高です。

EC2 のストレージ・ネットワーク機能とプレイスメントグループ 1.3.6

クラスターの容量不足
クラスタープレイスメントグループで InsufficientInstanceCapacity が出たら、グループ内のインスタンスをすべて停止してから起動し直すと、まとめて配置できる場所へ移る可能性があります。最初から必要台数を 1 回のリクエストで起動し、同じインスタンスタイプでそろえるのが原則。
拡張ネットワーキング（ENA）
現行世代のインスタンスで高帯域・低レイテンシーを実現するネットワークインターフェイス。ドライバーが必要。
EFA
Elastic Fabric Adapter。MPI などの HPC・機械学習のノード間通信向け。OS バイパスで低遅延。
ジャンボフレーム
VPC 内は MTU 9001 まで対応。インターネットや VPN 経由は 1500 以下になるため、経路の途中で MTU が下がる構成ではパケット分割や通信不良に注意。
EBS 最適化
現行世代は既定で EBS 専用帯域を持つ。インスタンスタイプごとに EBS 帯域・IOPS の上限があり、ボリュームより先にこちらが頭打ちになることがある。
インスタンスストア
物理ホストのローカルディスク。最速だが停止・終了・ホスト障害で消える。キャッシュや一時データ用。AMI 作成時にも中身は含まれない。
休止（Hibernate）
メモリの内容をルート EBS に保存して停止し、再開時に復元する。起動に時間のかかるアプリのウォームアップを省ける。ルートボリュームの暗号化が必要。

クラウド財務管理ツール 1.3.1

コストと TCO の「分析」そのものは受験対象者のタスク外とされていますが、Cost and Usage Reports・Cost Explorer・Savings Plans は対象サービスに含まれます。運用者としては「どのツールで何が分かるか」を区別できれば十分です。

可視化と予測
Cost Explorer

サービス・アカウント・タグ・使用タイプ別に最大過去 13 か月（設定で延長可）のコストをグラフ化し、将来を予測。Savings Plans／RI の購入推奨とサイズ適正化推奨も表示。

最も詳細なデータ
Cost and Usage Reports（Data Exports）

時間・リソース単位の明細を S3 に出力。Athena や QuickSight で分析。社内の課金配賦や独自ダッシュボードの基礎データ。

割引
Savings Plans

1 時間あたりの利用額をコミット。Compute（EC2・Fargate・Lambda に横断適用）と EC2 Instance（特定ファミリー）。使用率・カバー率は Cost Explorer で確認。

予算超過の通知
AWS Budgets

コスト・使用量・カバー率に予算を設定し、実績や予測がしきい値を超えたら通知。予算アクションで IAM ポリシーや SCP を適用して新規作成を止めることもできる。

異常の自動検知
Cost Anomaly Detection

機械学習で通常と異なる支出の急増を検知して通知。設定ミスによる想定外の課金に気付ける。

配賦
コスト配分タグ

タグを請求に反映させるには、請求コンソールでコスト配分タグとして有効化が必要。有効化以前のコストには遡って付かない。
