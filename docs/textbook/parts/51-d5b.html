Route 53：ホストゾーン・レコード・ルーティングポリシー 5.2.2

インターネット向け
パブリックホストゾーン

インターネットからの名前解決に回答。ドメインのレジストラで Route 53 の NS レコード（4 つのネームサーバー）を設定して委任します。

VPC 内向け
プライベートホストゾーン

関連付けた VPC の中からの問い合わせにだけ回答。VPC の enableDnsSupport と enableDnsHostnames が true であることが前提。別アカウントの VPC との関連付けは、承認（create-vpc-association-authorization）→ 関連付けの 2 段階を CLI／API で行います。

演習 PDF の論点（問題 24）

プライベートサブネットの DB サーバーにカスタムドメイン名 → プライベートホストゾーンに A レコード（値はプライベート IP）。IP アドレスを直接指すのは A／AAAA で、CNAME は別のドメイン名を指すときに使います。

クエリログと DNSSEC

パブリック DNS クエリログ
パブリックホストゾーンへの問い合わせを CloudWatch Logs へ記録。ロググループは us-east-1 に作り、Route 53 に書き込みを許すリソースポリシーが必要。
Resolver クエリログ
VPC 内のリソースが発行した DNS 問い合わせ（プライベートホストゾーンや外部ドメインを含む）を CloudWatch Logs・S3・Firehose へ。VPC 単位で関連付け、RAM で共有可能。
DNSSEC 署名
パブリックホストゾーンに署名し、DNS 応答の改ざんを防止。キー署名キーは us-east-1 の KMS（非対称キー）で管理し、親ゾーンに DS レコードを登録。
TTL
レコード変更の反映は TTL に左右される。切り替えを予定しているなら事前に TTL を短くしておく。

Route 53 Resolver とハイブリッド DNS 5.2.1

VPC には Amazon 提供の DNS リゾルバー（Route 53 Resolver）があり、VPC CIDR のベース＋2 のアドレス（例 10.0.0.2）または 169.254.169.253 で利用できます。オンプレミスと名前解決を連携させるには、向きに応じて 2 種類のエンドポイントを使い分けます。

インバウンドの SG
オンプレの DNS サーバーからの TCP／UDP 53 のインバウンドを許可。アウトバウンドは応答を返すため全ポートを許可するのが推奨。
アウトバウンドの SG
転送先 DNS サーバーへの TCP／UDP 53 のアウトバウンドを許可。
転送ルール
ドメインごとに転送先を指定し、VPC に関連付け。RAM で他アカウントの VPC と共有できる。「システムルール」で特定サブドメインだけ Resolver に解決させる例外も作れる。
オンプレ側の設定
AWS のゾーン名（例 example.internal）をインバウンドエンドポイントの IP へ転送する条件付きフォワーダーが必要。
演習 PDF の論点（問題 20）

オンプレミスの仮想サーバーから Route 53 のレコードを照会 → インバウンドエンドポイントを作り、オンプレ DNS からの TCP/UDP 53 のインバウンドを許可する SG を付ける。アウトバウンドエンドポイントは逆向き（VPC → オンプレ）です。

CloudFront によるコンテンツ配信とキャッシュ 5.2.3 5.3.3

キャッシュ保持期間（TTL）の決まり方

キャッシュ動作を構成するポリシー

ポリシー決めるものヒット率への影響
キャッシュポリシーTTL（最小・デフォルト・最大）とキャッシュキーに含めるクエリ文字列・ヘッダー・Cookie、圧縮キーに含める要素は「オリジンが内容を変えるのに使うものだけ」に絞る
オリジンリクエストポリシーキャッシュキーには含めずにオリジンへ転送する値オリジンが必要とする情報を渡しつつ、キャッシュは分割しない

キャッシュヒット率を上げる方法

  1. オリジンで長めの max-age を返す

    実用上許される最長の Cache-Control: max-age。更新はファイル名のバージョニングで対応。

  2. キャッシュキーを最小化

    必要なクエリ文字列だけを転送（順序や大文字小文字も統一）。Cookie・ヘッダーの全転送をやめる。User-Agent ではなく CloudFront-Is-Mobile-Viewer などのデバイス判定ヘッダーを使う。

  3. 静的と動的でキャッシュ動作を分ける

    パスパターン（/static/* など）ごとにキャッシュポリシーを分ける。

  4. Origin Shield を有効化

    複数のリージョナルエッジキャッシュからのミスを 1 つのキャッシュ層に集約し、オリジンへのリクエストを削減。

演習 PDF の論点（問題 23）

ヒット率向上 → 「オリジンが一意のオブジェクトを返すのに使うクエリ文字列だけを転送」と「max-age を実用的な最長値に」。署名付き URL／Cookie はアクセス制限のための機能で、ヒット率とは無関係です。

キャッシュの削除：無効化とバージョニング

即時に消したい
無効化（Invalidation）

aws cloudfront create-invalidation --distribution-id E1ABCD --paths "/images/photo.jpg" "/css/*"。エッジのキャッシュを期限前に破棄し、次のリクエストでオリジンから取り直させます。毎月一定数のパスまで無料で、超えると課金。ワイルドカードはパスの末尾に使えます。オリジンからファイルを消しただけでは、TTL が切れるまでエッジから配信され続けます。

日常の更新
ファイル名のバージョニング

app.v2.css のように名前を変えて参照先を更新。キャッシュを長く保てて無効化料金もかからず、ロールバックも容易。ただし既に配信された古い URL のキャッシュを消す手段ではありません。

演習 PDF の論点（問題 17）

誤って配信された写真をキャッシュから消す → 無効化が直接の手段。新しいバージョンのファイルを提供する方法もあわせて正解とされています。RTMP ディストリビューションは廃止済み、「CloudFront コマンドで手動削除」「S3 で配信無効化」は存在しない操作です。

OAC（オリジンアクセスコントロール）
S3 オリジンを CloudFront 経由でしか読めないようにする。旧方式の OAI の後継で、SSE-KMS の暗号化オブジェクトにも対応（キーポリシーで CloudFront を許可）。バケットポリシーは下の例。

VPC 設定のトラブルシューティング 5.3.1 5.3.4

インターネットから EC2 につながらない

  1. IGW とルート

    VPC に IGW がアタッチされ、サブネットのルートテーブルに 0.0.0.0/0 → igw- があるか（そのサブネットに関連付いた表か）。

  2. パブリック IP

    インスタンスにパブリック IPv4 か Elastic IP があるか。サブネットの自動割り当て設定、ASG の起動テンプレートの設定。

  3. セキュリティグループ

    インバウンドで送信元とポートを許可しているか。

  4. NACL

    インバウンドの許可と、アウトバウンドのエフェメラルポート。番号順に拒否ルールが先に当たっていないか。

  5. OS とアプリ

    OS のファイアウォール、サービスが起動して該当ポートで待ち受けているか。ここで初めてインスタンス内部を疑う。

プライベートサブネットから外に出られない

  1. プライベート側のルート

    0.0.0.0/0 → nat- があるか（IGW を向けても出られない）。

  2. NAT ゲートウェイの置き場所と状態

    パブリック NAT がパブリックサブネットにあり、そのサブネットのルートが IGW を向いているか。状態が Available か、EIP が付いているか。

  3. NACL と SG

    プライベート・パブリック両サブネットの NACL で、行きと戻り（エフェメラル）を許可しているか。インスタンスの SG のアウトバウンド。

VPC エンドポイント経由のアクセスが失敗する

  1. ゲートウェイ型

    エンドポイントがそのサブネットのルートテーブルに関連付けられているか、同じリージョンのバケットか、エンドポイントポリシーとバケットポリシーで許可しているか。

  2. インターフェイス型

    プライベート DNS が有効か（VPC の DNS 属性も true）、エンドポイントの SG がクライアントからの 443 を許可しているか、エンドポイントポリシー。

設定を静的に解析
VPC Reachability Analyzer

送信元と送信先（インスタンス、ENI、IGW、TGW など）を指定すると、実際にパケットを送らずに設定を解析し、到達できない場合はどの部品（SG、NACL、ルート）が原因かを示します。変更後の確認にも使えます。

意図しない経路の発見
Network Access Analyzer

「インターネットから DB サブネットへ到達できる経路がないこと」のような条件を定義し、それに反する経路を洗い出します。監査向け。パケットの中身を見たいなら Traffic Mirroring。

試験の着眼点：ACCEPT と REJECT の組み合わせで原因を当てる
  • 行き ACCEPT・戻り REJECT → 戻りを自動で許可する SG ではありえないので、NACL のアウトバウンド（ステートレス）が原因（演習 PDF 問題 11 の正解）。
  • 行きが REJECT → SG のインバウンドか NACL のインバウンド。どちらかは他の情報で判断。
  • フローログに記録されない通信：Amazon DNS サーバーへの問い合わせ、インスタンスメタデータ（169.254.169.254）、Time Sync、DHCP、Windows ライセンス認証など。
  • カスタム形式で vpc-id・subnet-id・tcp-flags・pkt-srcaddr（NAT 経由の元の送信元）・flow-direction・traffic-path などを追加できる。集約間隔は既定 10 分、1 分も選べる。

| sort rejects desc

CloudWatch のネットワーク監視サービス 5.3.5

SOA-C03 で新しく追加されたスキルです。「どこの、何の性能を測るか」で 3 つのサービスを区別します。

サービス測るもの仕組み典型的な問い
Internet Monitorインターネット上の利用者からアプリ（CloudFront、VPC、NLB など）までの可用性とパフォーマンスAWS が持つ世界のインターネット計測データを利用。都市×ネットワーク（ASN）単位で影響を表示し、ヘルスイベントを通知「特定の国・ISP の利用者だけ遅い」「インターネット側の障害かアプリ側か」
Network Synthetic MonitorAWS からオンプレミスなど特定の宛先へのハイブリッド経路の遅延とパケットロスVPC のサブネットから ICMP／TCP のプローブを送る（エージェント不要）。AWS 側の劣化かどうかを示すネットワークヘルス指標「Direct Connect／VPN 経由のオンプレ通信が遅い原因は AWS 側か」
Network Flow MonitorAWS 内のワークロード間（EC2、EKS など）の TCP 通信の性能インスタンスにエージェントを入れて TCP の再送やレイテンシーを計測。AZ 間・VPC 間・サービス宛ての流れを可視化「どのワークロード間の通信で再送が増えているか」
試験の着眼点：調べたいことから道具を選ぶ
  • 設定の誤りで通らない → Reachability Analyzer。
  • 通信は許可されているはずだが拒否されている記録を見たい → VPC フローログ。
  • つながるが遅い・不安定（オンプレ向け）→ Network Synthetic Monitor。
  • つながるが遅い（エンドユーザー側）→ Internet Monitor。
  • つながるが遅い（AWS 内のサービス間）→ Network Flow Monitor。
  • パケットの中身を見たい → Traffic Mirroring。
