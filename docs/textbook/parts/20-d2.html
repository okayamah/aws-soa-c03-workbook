EC2 Auto Scaling 2.1.1

Auto Scaling グループ（ASG）は「最小」「希望（desired）」「最大」の 3 つのキャパシティで動きます。スケーリングポリシーが変更するのは希望キャパシティで、その値は常に最小〜最大の範囲に収まります。最大が 1 なら、どんなポリシーを作っても 2 台目は起動しません。

スケーリングポリシーの種類

ポリシー動き選ぶ場面
ターゲット追跡指定メトリクスを目標値（例：平均 CPU 50%）に保つよう自動で増減。アラームは自動作成第一選択。予測できない負荷変動。定義済みメトリクスは ASGAverageCPUUtilization・ASGAverageNetworkIn/Out・ALBRequestCountPerTarget
ステップアラームの超過幅に応じて段階的に追加・削除（例：+20% で 1 台、+40% で 3 台）急激な負荷に大きく反応させたい
シンプルアラームごとに 1 つの調整。実行後はクールダウン（既定 300 秒）が終わるまで次を実行しない旧来方式。現在はステップかターゲット追跡が推奨
スケジュール日時を指定して最小・最大・希望を変更毎朝 9 時の出社、月末バッチなど予測できる負荷
予測スケーリング過去の負荷パターン（最低 24 時間、最大 14 日分）から機械学習で予測し、事前に起動日次・週次の周期的な負荷。まず「予測のみ」モードで精度を確認
演習 PDF の論点（問題 12）

最大キャパシティ 1 の ASG は実質スケールしない → 最大キャパシティを増やす。さらに CPU の高負荷に追従させるには、グループ全体の平均 CPU 使用率に基づくポリシーを追加します（「1 台が 90% を超えたら」という個別インスタンス基準のポリシーは作れません）。最小や希望を増やすのは常時の台数を増やすだけで、予測できないピークへの対策としては不適切です。

インスタンスのライフサイクル

運用で問われる設定

起動テンプレート
AMI・インスタンスタイプ・SG・ユーザーデータなどをバージョン管理。起動設定（Launch Configuration）は旧方式で新規作成できなくなっている。設定を変えるときは新バージョンを作る。
ヘルスチェック
既定は EC2 ステータスチェックのみ。ALB の背後なら ELB ヘルスチェックを有効化しないと、アプリが応答しなくても入れ替えられない。
ヘルスチェックの猶予期間
起動直後の初期化中に異常判定されないための待ち時間。短すぎると起動→異常→終了を繰り返す。
インスタンスのウォームアップ
新しいインスタンスが集約メトリクスに寄与し始めるまでの時間。過剰なスケールアウトを防ぐ。
終了ポリシー
既定はまず AZ 間の台数を均等にし、次に古い起動テンプレート／設定のものから終了。OldestInstance・NewestInstance・ClosestToNextInstanceHour などを指定可能。スケールインから保護したいインスタンスにはスケールイン保護。
インスタンスの更新
起動テンプレートの新バージョンへ、最小正常率を保ちながら順に置き換える（ローリング）。チェックポイント、アラームによる自動ロールバックに対応。
混合インスタンスポリシー
複数のインスタンスタイプとオンデマンド／スポットを組み合わせる。スポットの配分戦略は price-capacity-optimized が推奨。キャパシティの再調整で中断が近いスポットを先に置き換える。
プロセスの一時停止
Launch・Terminate・HealthCheck・ReplaceUnhealthy・AZRebalance などを止められる。調査のために異常インスタンスを残したいときは ReplaceUnhealthy を停止するか、Standby に移す。
最大インスタンス有効期間
一定期間を超えたインスタンスを自動で置き換え、長期稼働による劣化や設定ずれを防ぐ。

起動できない：InsufficientInstanceCapacity

特定の AZ で特定のインスタンスタイプの在庫が一時的に不足しているときに出るエラーです。ASG の台数設定を変えても AWS 側の在庫は増えません。

  1. 別の AZ でも起動できるようにする

    ASG に複数 AZ のサブネットを指定する。単一 AZ 指定をやめる。

  2. 別のインスタンスタイプも使えるようにする

    混合インスタンスポリシーで複数タイプを許可、起動テンプレートのタイプを変更。

  3. 時間をおいて再試行・リクエストを分割

    在庫は頻繁に変わる。大量の同時起動は小分けに。

  4. 確実性が必要ならキャパシティを予約

    オンデマンドキャパシティ予約で事前に確保する（使わなくても課金）。起動テンプレートで予約を対象にすれば ASG からも使えます。

演習 PDF の論点（問題 5）と補足

即効性のある対策として「インスタンスタイプを変える」「AZ を変える」が正解。PDF の解説はキャパシティ予約を「ASG には適用できない」としていますが、起動テンプレートでキャパシティ予約を指定する方法で ASG からも利用できます。設問の文脈（一時的なエラーへの対処、コスト）で不正解になっていると理解してください。

マネージドデータベースのスケーリング 2.1.3

Amazon RDS
RDS のスケール手段
  • 垂直：インスタンスクラスの変更（ダウンタイムあり。マルチ AZ ならスタンバイを先に変更してフェイルオーバーするため短い）。
  • 読み取り：リードレプリカ（非同期レプリケーション。別リージョンも可。昇格して独立 DB にできる）。
  • ストレージ：ストレージの自動スケーリング。空きが 10% 未満の状態が 5 分続き、前回変更から 6 時間経過していると、設定した上限まで自動拡張。
Amazon Aurora
Aurora のスケール手段
  • 最大 15 台の Aurora レプリカ。リーダーエンドポイントで読み取りを分散。
  • Aurora Auto Scaling：レプリカ数をターゲット追跡で増減。メトリクスはリーダーの平均 CPU（RDSReaderAverageCPUUtilization）か平均接続数（RDSReaderAverageDatabaseConnections）。ライターは計算に含まれない。
  • ストレージは自動で拡張（容量の事前確保は不要）。
  • Aurora Serverless v2：ACU（Aurora キャパシティユニット）単位で秒単位に伸縮。プロビジョンドのインスタンスと同じクラスターに混在できる。
演習 PDF の論点（問題 13）

接続数 1,200 で性能が落ちる Aurora → Aurora Auto Scaling のターゲット値を1,000（性能劣化の手前）にする。新しいレプリカが使えるようになるまで数分かかるため、限界値そのもの（1,200）をターゲットにすると間に合いません。レプリカの昇格はフェイルオーバーの仕組みでスケーリングではありません。

ターゲットが Unhealthy になる原因

  1. セキュリティグループ

    ターゲットの SG が、ALB の SG（またはサブネット CIDR）からのヘルスチェックポートを許可しているか。NACL の戻り（エフェメラルポート）も確認。

  2. パスと応答コード

    ヘルスチェックパスが存在し、Matcher のコードを返しているか（リダイレクトや認証で 301/302/401 になっていないか）。

  3. アプリの起動とポート

    アプリがヘルスチェックのポートで待ち受けているか。起動に時間がかかるなら ASG のヘルスチェック猶予期間を延ばす。

  4. タイムアウト

    依存先（DB など）が遅くてヘルスチェックの Timeout を超えていないか。

アクセスログ
既定で無効。S3 に出力（バケットポリシーで ELB のログ配信を許可）。各リクエストの処理時間、ELB とターゲットの応答コードが分かる（読み方は第 5 章）。
その他のメトリクス
TargetResponseTime・HealthyHostCount／UnHealthyHostCount・RejectedConnectionCount（ALB の接続上限）・RequestCount。

マルチ AZ と耐障害性 2.2.2

RDS マルチ AZ の自動フェイルオーバー
プライマリの AZ 障害、インスタンスの障害、インスタンスクラスの変更、OS パッチ適用、「フェイルオーバーありの再起動」で発生。エンドポイント（DNS 名）は変わらず、指す先が切り替わる。アプリは DNS の再解決と再接続が必要（RDS Proxy で短縮）。
Aurora
データは 3 AZ に 6 コピー。ライター障害時はレプリカを昇格（優先度ティア 0〜15 の小さいものから）。レプリカがなければ新しいライターを作り直すため時間がかかる → 別 AZ に最低 1 台のレプリカを置く。
Aurora グローバルデータベース
リージョン間で 1 秒未満のレプリケーション。リージョン障害時はセカンダリリージョンを昇格（計画的な切り替えと、障害時のフェイルオーバーの 2 方式）。
ElastiCache
Valkey／Redis でマルチ AZ ＋自動フェイルオーバーを有効化し、レプリカを別 AZ に置く。
EC2 と ASG
ASG に複数 AZ のサブネットを指定。AZ の台数が偏ると AZ リバランスで均等化。
NAT ゲートウェイ
従来の NAT ゲートウェイはAZ 単位のリソース。AZ ごとに作り、各 AZ のプライベートサブネットは同じ AZ の NAT を向けないと、その AZ の障害で全体の外向き通信が止まる。2025 年 11 月からは複数 AZ に自動で広がるリージョナル NAT ゲートウェイも選べる。
EFS／S3／DynamoDB
リージョンサービスで、標準で複数 AZ に冗長化（EFS One Zone と S3 One Zone-IA は除く）。
Application Recovery Controller
ゾーンシフトで、障害の兆候がある AZ への ALB／NLB のトラフィックを一時的に止める。ゾーンオートシフトを有効にすると、AWS が AZ の障害を検知したときに自動でシフト。ルーティングコントロールで、リージョン間の切り替えを安全なスイッチとして扱える。
演習 PDF の論点（問題 7 の誤答）

「性能改善のためにマルチ AZ を有効化」は誤り。マルチ AZ 配置のスタンバイは読み取りを受け付けないため、性能は上がりません。

AWS Backup とスナップショットの自動化 2.3.1

ライフサイクル
N 日後にコールドストレージへ移行、M 日後に削除。コールドストレージは最低 90 日保持が必要なので、削除日は「移行日＋90 日」以上。コールドに対応するリソースは EFS、DynamoDB（高度な機能）、EBS、S3 などに限られる。
Vault Lock
ボールト内のバックアップを削除・保持期間の短縮から守る（WORM）。ガバナンスモードは十分な権限があれば解除可能、コンプライアンスモードは猶予期間（最低 72 時間）経過後は誰も解除できない。
論理的にエアギャップされたボールト
別アカウントと共有でき、AWS が管理するキーでロック状態になる。ランサムウェアからの復旧用。
組織での一元管理
Organizations のバックアップポリシーで、全アカウントに同じプランを強制。委任管理者でクロスアカウントの監視。
Backup Audit Manager
「すべての RDS が毎日バックアップされているか」「保持期間が 35 日以上か」などをフレームワークとして評価しレポート。
復元テスト
定期的に自動で復元を実行し、バックアップが実際に使えるか検証。
Data Lifecycle Manager との違い
DLM は EBS スナップショットと EBS-backed AMI 専用でシンプル。複数サービスをまとめ、監査・クロスアカウントコピー・ロックまで必要なら AWS Backup。
演習 PDF の論点（問題 16）
  • 「24 時間ごと・1 年後にコールドストレージ・暗号化」→ カスタマーマネージドキーで暗号化したボールトを作成し、日次ルールとライフサイクル（365 日でコールド）を持つバックアッププランに DynamoDB テーブルを割り当てる。スケジュールやライフサイクルはボールトではなくプランの設定です。
  • DynamoDB の PITR は過去 35 日以内の任意時点への復元で、日次スケジュールやコールド移行の機能はありません。
  • AWS Backup から DynamoDB を復元すると、Auto Scaling ポリシー、タグ、IAM ポリシー、CloudWatch アラーム、TTL、ストリーム設定は復元されないので、IaC やスクリプトで再適用する準備をしておきます。

データベースの復元と RTO・RPO 2.3.2

RPO（目標復旧時点）は「どこまで遡ってデータを失ってよいか」、RTO（目標復旧時間）は「どれだけの時間で復旧すべきか」です。復元方法は、この 2 つとコストの兼ね合いで選びます。

方法復元できる範囲RPO の目安RTO と注意点
RDS 自動バックアップ（PITR）保持期間（1〜35 日）内の任意の時点約 5 分新インスタンス作成のため数十分。保持期間 0 で無効化。別リージョンへの自動バックアップレプリケーションも可
RDS 手動スナップショット取得時点取得間隔に依存削除するまで保持（35 日を超えて残せる）。別リージョン・別アカウントへコピー／共有可能（暗号化済みならカスタマーマネージドキーの共有も必要）
Aurora バックトラック最大 72 時間前まで秒単位新クラスターを作らず同じクラスターを巻き戻すので最速。Aurora MySQL のみ
Aurora クローン現時点のコピー—コピーオンライトで高速に複製。検証用環境に
DynamoDB PITR過去 1〜35 日（期間は設定可能）の任意の秒秒単位新しいテーブルとして復元
DynamoDB オンデマンドバックアップ取得時点取得間隔に依存長期保存。AWS Backup 経由ならコールド移行・リージョン間コピー
Aurora グローバルデータベースセカンダリリージョン通常 1 秒未満リージョン障害時に 1 分程度で昇格
ひっかけ注意
  • RDS の復元で「既存のインスタンスに上書き」はできません。復元後に DNS（Route 53 の CNAME）やアプリの設定で接続先を切り替えます。
  • リードレプリカがある RDS では自動バックアップを無効化（保持期間 0）できません。
  • 暗号化されていない RDS を暗号化するには、スナップショット → 暗号化を指定してコピー → そこから復元、の手順です。

ストレージのバージョニング 2.3.3

Amazon S3
S3 バージョニング
  • 状態は「未設定 → 有効 → 停止」。一度有効にすると未設定には戻せない（停止のみ）。
  • 削除するとオブジェクトは消えず削除マーカーが付く。削除マーカーを消せば復活。特定のバージョン ID を指定した削除は完全削除。
  • 古いバージョンも課金対象 → ライフサイクルの「非現行バージョン」ルールで移行・削除。
  • MFA Delete：バージョンの完全削除とバージョニング状態の変更に MFA を要求。ルートユーザーが CLI／API で設定。
  • レプリケーション（CRR／SRR）は送信元・送信先の両方でバージョニングが必須。
Amazon FSx
FSx のバージョン管理
  • FSx for Windows File Server：シャドウコピー（VSS）を有効にすると、利用者が Windows エクスプローラーの「以前のバージョン」から自分で復元できる。
  • FSx for NetApp ONTAP：ボリュームのスナップショットを定期取得。.snapshot ディレクトリから復元。
  • どちらも自動日次バックアップ（保持期間設定）と AWS Backup に対応。

ガバナンスモードでロックされたオブジェクトを削除するには、s3:BypassGovernanceRetention 権限と、リクエストでのバイパスの明示（ヘッダー x-amz-bypass-governance-retention: true、CLI では aws s3api delete-object ... --bypass-governance-retention）の両方が必要です。PDF の選択肢には綴りの誤り（retertion）がありますが、正しくは retention です。

試験の着眼点：DR 手順のベストプラクティス
  • 復旧手順はIaC とランブックでコード化し、定期的に訓練（復元テスト・フェイルオーバー演習）する。手順書を読みながらの手作業は RTO を守れない原因になります。
  • AMI、KMS キー、シークレット、パラメーターなど「リージョンに閉じたもの」を DR リージョンにも用意しておく（AMI のコピー、マルチリージョンキー、Secrets Manager のレプリカ）。
  • サービスクォータは DR リージョンでも引き上げておく。いざというときに起動できない原因になります。
