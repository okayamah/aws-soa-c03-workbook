IAM の機能 4.1.1

機能要点
パスワードポリシーアカウント単位で IAM ユーザーのパスワード要件（最小長、文字種、有効期限、再利用禁止、期限切れ時の管理者リセット要否）を設定。ルートユーザーには適用されない
MFA仮想 MFA、パスキー／FIDO2 セキュリティキー、ハードウェア TOTP。ルートユーザーには必須。ポリシーで aws:MultiFactorAuthPresent（MFA 済みか）・aws:MultiFactorAuthAge（何秒前に認証したか）を条件にできる
ロール一時的な認証情報を発行する ID。信頼ポリシー（誰が引き受けられるか）と権限ポリシー（何ができるか）の 2 つで構成。EC2 にはインスタンスプロファイル経由で渡す。セッションの既定は 1 時間、最大 12 時間（ロールの連鎖は 1 時間まで）

フェデレーションSAML 2.0（社内 IdP）、OIDC（GitHub Actions、ウェブ ID）。複数アカウントへの人のアクセスは IAM Identity Center が推奨
リソースベースのポリシーS3 バケットポリシー、KMS キーポリシー、SQS／SNS のアクセスポリシー、Lambda の関数ポリシーなど。Principal を指定し、クロスアカウントのアクセスを許可できる
アクセス許可の境界ユーザー／ロールに付けられる権限の上限。開発者に IAM ロール作成を任せつつ、自分より強い権限を作らせない用途
条件キーaws:SourceIp・aws:RequestedRegion・aws:PrincipalOrgID・aws:SecureTransport・aws:SourceVpce・aws:ResourceTag／aws:RequestTag／aws:PrincipalTag（ABAC）・kms:ViaService など

ポリシー評価ロジック 4.1.1 4.1.3

ひっかけ注意
  • SCP は管理アカウントには効かず、サービスにリンクされたロールにも効きません。メンバーアカウントのルートユーザーには効きます。
  • SCP で許可（Allow）を書いても権限は付与されません。各アカウントの IAM ポリシーで許可が必要です。
  • KMS キーはキーポリシーが主役です。キーポリシーがアカウント（arn:aws:iam::ACCOUNT:root）を信頼していない限り、IAM ポリシーで kms:* を許可しても使えません。

  1. 誰として呼んでいるかを確認

    aws sts get-caller-identity。想定と違うロールやプロファイルで実行していることは多い。

  2. 明示的な拒否を探す

    SCP、権限境界、リソースポリシー、VPC エンドポイントポリシー、セッションポリシーのどこかに Deny がないか。

  3. 許可の有無を確認

    アイデンティティポリシーにアクションとリソース ARN が含まれるか、条件（MFA、IP、タグ、リージョン）を満たしているか。

  4. リソース側の許可

    クロスアカウントならバケットポリシーやキーポリシーで相手を許可しているか。KMS で暗号化されたオブジェクトはキーの使用許可も必要。

  5. シミュレーターで再現・修正を検証

    修正案を Policy Simulator や Access Analyzer のポリシーチェックで確認してから適用。

IAM Identity Center

組織の全アカウントへのシングルサインオン。許可セット（権限の定義）をユーザー／グループとアカウントの組み合わせに割り当てると、各アカウントに IAM ロールが自動で作られます。ID ソースは Identity Center のディレクトリ、Active Directory、外部 IdP（SAML＋SCIM で自動同期）。アカウントごとに IAM ユーザーを作る運用を置き換えます。

Trusted Advisor のセキュリティチェックと修復 4.1.4

Trusted Advisor はコスト・パフォーマンス・セキュリティ・耐障害性・サービスクォータ・運用上の優秀性の観点でアカウントを点検します。ベーシック／デベロッパーサポートでは一部の中核的なセキュリティチェックとサービスクォータのチェックのみ、ビジネス以上で全チェックと API・組織ビューが使えます。

チェック何が問題か修復
セキュリティグループ - 無制限アクセスの特定ポート22（SSH）、3389（RDP）などが 0.0.0.0/0 に開いている送信元を管理用 CIDR に絞る、Session Manager に置き換えてポートを閉じる
Amazon S3 バケットのアクセス許可バケットが公開・誰でも書き込み可能S3 ブロックパブリックアクセスを有効化、バケットポリシーと ACL の見直し
ルートアカウントの MFAルートユーザーに MFA がないMFA を有効化し、ルートのアクセスキーは削除
IAM の使用IAM ユーザー等がなくルートを使っている管理者ユーザーまたは Identity Center を用意し、ルートの日常利用をやめる
IAM パスワードポリシーポリシー未設定・弱い長さ・文字種・再利用禁止を設定
IAM アクセスキーのローテーション90 日以上ローテーションされていない新キー作成 → アプリを切り替え → 旧キーを無効化 → 削除。可能ならロールに置き換え
漏洩したアクセスキー公開リポジトリ等でキーが見つかった直ちに無効化・削除し、CloudTrail で不正利用を確認。Health の AWS_RISK_CREDENTIALS_EXPOSED イベントを EventBridge で受けて自動対応も可能
EBS／RDS のパブリックスナップショットスナップショットが全員に公開共有設定をプライベートに変更。宣言型ポリシーやブロック設定で再発防止
CloudTrail のログ記録証跡がない・一部リージョンのみ全リージョンの証跡（組織の証跡）を作成
ELB のリスナーセキュリティ古い暗号化方式や HTTP のみ推奨セキュリティポリシーの HTTPS リスナー、HTTP→HTTPS リダイレクト
試験の着眼点

Trusted Advisor のチェック結果の変化は EventBridge（us-east-1）で受け取れます。「チェックが赤になったら自動で修復」なら EventBridge → Lambda／SSM Automation。サービスクォータの使用率に関するチェックは、上限に達して起動できなくなる前に Service Quotas で引き上げを申請するきっかけになります。

コンプライアンス要件と継続的モニタリング（AWS Config） 4.1.5

Config はリソースの設定項目（Configuration Item）を記録し、変更履歴のタイムラインと、ルールに照らした準拠／非準拠を継続的に評価します。CloudTrail が「操作の記録」なら、Config は「状態の記録と評価」です。

レコーダーと配信チャネル
記録対象のリソースタイプを選び（全リソース推奨）、設定履歴とスナップショットを S3 へ、変更通知を SNS へ。記録頻度は「継続的」か「日次（定期）」でコストを調整。
マネージドルール
AWS 提供のルール。例：restricted-ssh、s3-bucket-public-read-prohibited、encrypted-volumes、required-tags、rds-multi-az-support、cloudtrail-enabled、iam-password-policy。
カスタムルール
Lambda、または Guard（ポリシー言語）で独自のチェックを書く。
トリガー
「設定変更時」と「定期実行（1・3・6・12・24 時間）」。
修復
ルールに SSM Automation ランブックを関連付け、手動または自動修復（再試行回数を設定）。
コンフォーマンスパック
ルールと修復アクションを 1 つのパッケージ（YAML テンプレート）にまとめ、アカウントや組織全体へ一括展開。「Operational Best Practices for CIS／PCI DSS／NIST」などのサンプルがある。準拠スコアで全体の状況を把握。
アグリゲーター
複数アカウント・複数リージョンの Config データを 1 か所に集約して表示。
高度なクエリ
SQL ライクな構文で現在の設定を検索（例：暗号化されていない EBS の一覧）。
プロアクティブ評価
リソースを作成する前に、ルールに照らして評価（CloudFormation Hooks と連携）。
試験の着眼点：リージョンとサービスの選択
  • 「データは日本国内にとどめる」→ SCP の aws:RequestedRegion で他リージョンの利用を拒否し、Config で準拠を継続監視。
  • 「特定のコンプライアンス基準への準拠を証明」→ コンフォーマンスパックで継続評価し、AWS の第三者監査レポートは AWS Artifact から取得。
  • 「承認されていないサービスの利用を禁止」→ SCP の許可リスト方式、または特定サービスを Deny。
演習 PDF の論点（問題 10）

「環境の構成変更を監視してログを取得」→ Config。VPC 内の全トラフィックの監視と防御 → 専用サブネットに配置した Network Firewall にルートテーブルで全トラフィックを通す（WAF は Web アプリ向け）。

データ分類スキーム 4.2.1

データ分類は「どのデータがどの機密度か」をラベル付けし、そのラベルに応じた保護（暗号化、アクセス制御、保持）を機械的に適用できるようにすることです。AWS での実装はタグと自動検出の組み合わせです。

ラベル付け
タグによる分類
  • DataClassification=Confidential のようなタグをバケット・テーブル・ボリュームに付与。
  • タグポリシーで値の表記を統一、Config の required-tags で付け忘れを検出。
  • ABAC：aws:ResourceTag/DataClassification と aws:PrincipalTag を条件にしてアクセスを制御。
  • AWS Backup のリソース割り当てもタグで行える（機密度ごとに保持期間を変える）。
自動検出
Amazon Macie
  • S3 内の個人情報・認証情報・金融情報などの機微データを機械学習とパターンで検出。
  • 自動検出（バケット全体を継続的にサンプリング）と、対象を指定する検出ジョブ。
  • マネージドデータ識別子に加え、正規表現のカスタムデータ識別子（社員番号など）。
  • 検出結果は EventBridge・Security Hub へ。バケットが公開・未暗号化であることも報告。

保管中の暗号化（AWS KMS） 4.2.2

キーの種類キーポリシーの管理ローテーション使いどころ
AWS 所有キー不可（見えない）AWS が管理既定の暗号化（SSE-S3、DynamoDB の既定など）
AWS マネージドキー（aws/ebs など）不可毎年自動手軽な暗号化。ただし他アカウントと共有できない、キーポリシーを変えられない
カスタマーマネージドキー可任意で自動（期間 90〜2,560 日）＋オンデマンドクロスアカウント共有、細かいアクセス制御、監査、削除や無効化の管理が必要な場合
キーポリシー
既定のポリシーにはアカウント（:root）に kms:* を許可する文があり、これによって IAM ポリシーでのキー権限付与が有効になる。キー管理者とキー利用者を分けて記述。
グラント
一時的・プログラム的な権限委譲。EBS や RDS などのサービスが内部で使う。
kms:ViaService
「S3 経由でのみこのキーを使える」のように、キーの利用を特定サービスからの呼び出しに限定する条件キー。
削除
即時削除はできず 7〜30 日の待機期間を経て削除。待機中はキャンセル可能。削除するとそのキーで暗号化したデータは二度と復号できないので、まずは「無効化」で影響を確認。
インポートしたキーマテリアル
自動ローテーション不可（手動で新しいキーに切り替え）。有効期限を設定できる。
マルチリージョンキー
同じキーマテリアルを複数リージョンに複製。リージョン間で暗号化データをそのまま復号できる（DR 用）。
スロットリング
KMS の API にはリクエストクォータがある。大量の S3 オブジェクトで SSE-KMS を使うなら S3 バケットキーで KMS 呼び出しを大幅に削減。

よく問われる暗号化の操作

やりたいこと方法
既存の未暗号化 EBS を暗号化スナップショット → 暗号化を指定してコピー → 新ボリュームを作成して付け替え。今後はリージョンの「EBS 暗号化をデフォルトにする」を有効化
既存の未暗号化 RDS を暗号化スナップショット → 暗号化コピー → 復元（新インスタンス）。リードレプリカはソースと同じ暗号化状態
暗号化スナップショットを別アカウントへ共有カスタマーマネージドキーで暗号化し、キーポリシーで相手アカウントに使用を許可してからスナップショットを共有
暗号化スナップショットを別リージョンへコピーコピー時に送信先リージョンのキーを指定（KMS キーはリージョン単位。マルチリージョンキーなら同じキーとして扱える）
S3 で暗号化されていないアップロードを拒否既定の暗号化（SSE-S3 は既に標準）。特定のキーを強制するならバケットポリシーで s3:x-amz-server-side-encryption-aws-kms-key-id を条件に Deny
EFS を暗号化作成時のみ設定可能。既存は新しい暗号化済み EFS を作り DataSync でデータを移す
ひっかけ注意：暗号化と権限

SSE-KMS で暗号化された S3 オブジェクトの GetObject が AccessDenied になる → バケットポリシーや IAM が許可していても、KMS キーの kms:Decrypt 権限がなければ失敗します。クロスアカウントでは特に見落とされがちです。

転送中の暗号化（ACM ほか） 4.2.3

項目要点
ACM のパブリック証明書ACM と統合されたサービス（ELB、CloudFront、API Gateway など）で使う分は無料。DNS 検証（Route 53 に CNAME を作る）なら自動更新される。メール検証は更新時にも承認が必要
自動更新期限の 60 日前から更新を試みる。DNS 検証の CNAME を消していたり、証明書がどのリソースにも関連付けられていないと更新できない
インポートした証明書サードパーティの証明書は自動更新されない。DaysToExpiry メトリクスや期限切れ前の EventBridge イベント（既定 45 日前）で監視し、手動で再インポート
リージョンACM 証明書はリージョン単位。CloudFront で使う証明書は us-east-1 で発行・インポート。ALB で使うなら ALB と同じリージョン
ELBHTTPS／TLS リスナーに証明書を設定し、セキュリティポリシー（TLS バージョンと暗号スイート）を選択。ALB は SNI で複数証明書。HTTP リスナーは HTTPS へリダイレクト。必要ならターゲットまで再暗号化（エンドツーエンド）
CloudFrontビューワープロトコルポリシー（HTTPS へリダイレクト／HTTPS のみ）、オリジンプロトコルポリシー（オリジンまでも HTTPS）
RDSSSL/TLS 接続を強制：PostgreSQL は rds.force_ssl=1、MySQL は require_secure_transport=ON（パラメータグループ）
S3バケットポリシーで aws:SecureTransport が false のリクエストを Deny
プライベート CAAWS Private CA で社内向け証明書を発行し、ACM で管理
 
// HTTPS 以外のアクセスを拒否するバケットポリシー
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "DenyInsecureTransport",
    "Effect": "Deny",
    "Principal": "*",
    "Action": "s3:*",
    "Resource": ["arn:aws:s3:::todo-assets", "arn:aws:s3:::todo-assets/*"],
    "Condition": { "Bool": { "aws:SecureTransport": "false" } }
  }]
}

ひっかけ注意

最新動向：Security Hub の名称

従来の Security Hub はコントロール評価を中心とする Security Hub CSPM という名称になり、新しい Security Hub は GuardDuty・Inspector・Macie・CSPM の結果を相関させ、実際に悪用されうる「露出」を優先順位付きで示す統合画面として提供されています。試験の選択肢ではどちらも「Security Hub」と表記されうるので、「複数サービスの検出結果を集約し優先順位付けする場所」と理解しておけば判断できます。

Security Hub の運用設定

委任管理者と中央設定
Organizations の委任管理者アカウントで中央設定を有効にし、設定ポリシーで「どの標準・コントロールをどのアカウント／OU で有効にするか」を一元管理。
クロスリージョン集約
ホーム（集約）リージョンを決め、リンクしたリージョンの検出結果をそこへ集める。
統合されたコントロールの検出結果
同じコントロールが複数の標準に含まれていても、検出結果を 1 つにまとめる設定。管理者アカウントで有効にするとメンバーにも適用される。
自動化ルール
条件に一致する検出結果の重要度を変更したり、抑制したりする（ノイズ削減）。
カスタムアクション
コンソールで選んだ検出結果を EventBridge に送り、手動トリガーで修復を実行。
演習 PDF の論点（問題 6）

リージョン集約は設定済みなのに、標準ごとに検出結果がばらばらに出る → 管理者アカウントで「統合されたコントロールの検出結果」を有効化。中央設定は管理方式、ホーム／リンクリージョンは集約先の設定で、検出結果の統合とは別の機能です。

GuardDuty の運用

検出結果タイプ
脅威の目的:リソース/詳細 の形式。例：UnauthorizedAccess:EC2/SSHBruteForce、CryptoCurrency:EC2/BitcoinTool.B!DNS、UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration。
重要度
低・中・高・重大。EventBridge のパターンで重要度の数値を条件にできる。
抑制ルール
既知の正常な動作（脆弱性スキャナーなど）による検出結果を自動アーカイブ。
信頼できる IP リスト／脅威リスト
自社の IP を除外、独自の脅威インテリジェンスを追加。
マルチアカウント
委任管理者で組織の全アカウントを自動有効化。
侵害インスタンスの対応例
EventBridge → Lambda で、通信を遮断する隔離用 SG に付け替え、EBS スナップショットを取得し（証拠保全）、ASG から切り離して調査。
