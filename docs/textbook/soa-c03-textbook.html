試験の全体像

SOA-C03 は 2025 年 9 月 30 日に始まった、旧 SysOps Administrator – Associate（SOA-C02）の後継試験です。名称が「CloudOps Engineer」に変わり、コンテナ（ECS/EKS）、CDK、マルチアカウント運用、AI を使った運用支援が範囲に加わりました。試験は「設計する人」ではなく動いているワークロードを監視し、壊れたら直し、自動化で再発を防ぐ人を想定しています。設問の多くは「障害やエラーが起きている」「要件が追加された」という状況から始まり、最も運用負荷が小さく確実な対処を選ばせます。

解き方の型

SOA-C03 の設問は、長い状況説明の最後に「最も運用効率が高い方法は」「最もコスト効率が高い方法は」といった評価軸が付きます。複数の選択肢が技術的には動くため、評価軸に合わないものを落としていくのが基本の解き方です。

できるだけ早く／即時に無効化（Invalidation）、Patch now、オンデマンド実行、フェイルオーバーの手動実行TTL 切れを待つ、次回のメンテナンスウィンドウを待つ

    「2 つ選択」「最もコスト効率」など、答えの数と評価軸を確定させます。

  2. 状況説明から「制約」を抜き出す

    リージョン数、マルチ AZ か、暗号化の有無、既存サービス（ASG・ALB・CloudFront など）、予測可能な負荷か否か。ここに正解の根拠がほぼ書かれています。

    最後に見直し時間を 15〜20 分残す配分が目安です。

CloudWatch メトリクスの仕組み 1.1.1

メトリクスは「名前空間（例 AWS/EC2）＋メトリクス名（例 CPUUtilization）＋ディメンション（例 InstanceId=i-0abc）」の組で一意になる時系列データです。ディメンションが 1 つでも違えば別のメトリクスとして扱われるため、アラームで「データが来ない」原因の多くはディメンションの指定ミスです。メトリクスは削除できず、保持期間が過ぎると自動的に消えます。

保持期間とロールアップ

300 秒（5 分）63 日EC2 基本モニタリングは 5 分間隔

統計と高度な機能

統計
Average・Sum・Minimum・Maximum・SampleCount・パーセンタイル（p90, p99 など）。レイテンシーは平均より p99 の方が利用者の体感に近い。
カスタムメトリクス
PutMetricData API（または CLI aws cloudwatch put-metric-data）。ディメンションは最大 30。標準解像度（60 秒）か高解像度（1 秒）を選ぶ。
EMF
Embedded Metric Format。Lambda などで構造化 JSON ログを書くだけで、CloudWatch が自動的にメトリクスを抽出する。API 呼び出しを増やさずにカスタムメトリクスを出せる。
メトリクス数式
複数メトリクスの演算（例：errors / requests * 100 でエラー率）。結果にアラームを設定できる。
異常検出
過去データから期待値の帯（バンド）を機械学習で作り、帯を外れたら ALARM。季節性のある指標で固定しきい値が使いにくいときに使う。
Metrics Insights
SQL 風のクエリで多数のメトリクスを集約（例：全インスタンスの CPU 上位 10）。クエリ結果にアラームを設定でき、インスタンスが増減しても追従する。

アラームの評価と複合アラーム 1.1.3

アラームは 3 つの状態（OK・ALARM・INSUFFICIENT_DATA）を持ち、状態が遷移したときにだけアクションを実行します。ALARM のまま続いても通知は繰り返されません。評価のパラメータは「期間（Period）」「評価期間数（N）」「アラームを発生させるデータポイント数（M）」の 3 つで、直近 N 期間のうち M 個がしきい値を超えたら ALARM になります。

設定欠落データの解釈向いている場面

EC2 アクションの使い分け

StatusCheckFailed_System
システムステータスチェック失敗 → 復旧（Recover）

AWS 側のハードウェア・電源・ネットワークの問題。recover アクションで別の物理ホストへ移り、インスタンス ID・プライベート IP・Elastic IP・メタデータは維持されます（EBS ボリュームのみのインスタンスが対象）。手動なら停止→起動でもホストが変わります（再起動ではホストは変わらない）。

StatusCheckFailed_Instance
インスタンスステータスチェック失敗 → 再起動（Reboot）

OS 側の問題（カーネルパニック、メモリ枯渇、ファイルシステム破損、ネットワーク設定の誤り）。reboot アクションか、ログ確認・EC2Rescue による調査で対処します。

試験の着眼点：アラームの EC2 アクション
  • アイドル状態のインスタンスを自動停止してコスト削減 → CPUUtilization の Average にアラームを設定し、EC2 アクション「停止」。Run Command で CPU を取りに行く案、フローログから CPU を読む案は不可能です。
  • EC2 アクションの初回作成時、CloudWatch はサービスにリンクされたロール AWSServiceRoleForCloudWatchEvents を自動作成して停止などを代行します。
  • AWS 起因のハードウェア劣化・予定メンテナンスは CloudWatch ではなく AWS Health のイベントとして通知されます（後述）。

複合アラーム（Composite Alarm）

複数のアラームの状態を AND・OR・NOT で組み合わせたルール式で判定します。例：ALARM("cpu-high") AND ALARM("latency-high")。CPU が高いだけ、レイテンシーが高いだけでは通知せず、両方そろったときだけ担当者を呼ぶ、というアラーム疲れの削減が主目的です。さらに「アクション抑制」を設定すると、メンテナンス用アラームが ALARM の間は通知を止められます。複合アラームは EC2 アクションと Auto Scaling アクションを持てない点に注意してください。

アラームが期待どおり動かないときの調査順

  1. INSUFFICIENT_DATA のまま

    名前空間・メトリクス名・ディメンションの一致を確認。期間がメトリクスの発行間隔より短くないか（5 分間隔のメトリクスに 1 分期間など）。エージェントやアプリが実際に送信しているか。

  2. ALARM になるのに通知が来ない

    SNS サブスクリプションが「確認済み」か。アラームのアクションが無効化（disable-alarm-actions）されていないか。SNS トピックが KMS で暗号化されている場合、キーポリシーで cloudwatch.amazonaws.com に kms:Decrypt・kms:GenerateDataKey* を許可しているか（AWS マネージドキー aws/sns ではこの許可を付けられないため、カスタマーマネージドキーが必要）。

  3. 一度しか通知されない

    仕様です。アクションは状態遷移時のみ実行されます。繰り返し通知したいなら、EventBridge Scheduler などで別途仕組みを作ります。

  4. 想定より早く／遅く発火する

    統計（Average と Maximum の取り違え）、M/N の設定、欠落データの扱いを見直します。

ダッシュボードとクロスアカウント監視 1.1.4

CloudWatch ダッシュボードはグローバルなリソースで、1 つのダッシュボードに複数リージョンのウィジェットを並べられます。複数アカウントのメトリクスを 1 か所で見るには、CloudWatch クロスアカウントオブザーバビリティを設定します。

推奨
クロスアカウントオブザーバビリティ

「モニタリングアカウント」にシンク（sink）を作り、各「ソースアカウント」からリンクを張ります。メトリクス・ログ・トレース・Application Signals を共有でき、Organizations の OU 単位でまとめて設定できます。モニタリングアカウント側でダッシュボードやアラームを作れば全アカウント横断になります。

従来方式
クロスアカウント・クロスリージョンのコンソール

共有元アカウントに CloudWatch-CrossAccountSharingRole を作り、閲覧側のコンソールでアカウントを切り替えて表示します。ダッシュボード上でアカウント ID を指定したウィジェットも作れます。

共有
ダッシュボードは「公開（リンクを知る誰でも）」「指定したメールアドレス（ログインが必要）」「SSO プロバイダー経由」の 3 通りで共有できます。AWS アカウントを持たない関係者にも見せられます。
変数
ダッシュボード変数を使うと、インスタンス ID などをドロップダウンで切り替えて 1 つのダッシュボードを使い回せます。
IaC 化
AWS::CloudWatch::Dashboard の DashboardBody（JSON）でテンプレート化できます。アカウントごとに同じダッシュボードを配るなら StackSets を使います。
自動ダッシュボード
サービスごとの推奨メトリクスを並べたダッシュボードが自動で用意されています。カスタムの出発点として便利です。
ハンズオン（リポジトリ Week 1）

CloudWatch Logs：フィルター・集約・分析 1.1.1

ログは「ロググループ」（アプリや用途の単位）と「ログストリーム」（インスタンスやコンテナなど送信元の単位）の 2 階層で保存されます。保持期間はロググループごとに設定し、既定は「失効しない」なのでコストが膨らみがちです。1 日〜10 年の範囲で必ず設定します。

機能何をするか試験で問われる要点
メトリクスフィルターログの文字列パターン（例 ERROR、JSON の { $.status = 500 }）に一致した件数や値をメトリクス化作成後に届いたログにだけ適用（過去ログは遡らない）。アラームと組み合わせて「エラーが 5 分で 10 件以上」を検知。
サブスクリプションフィルター一致したログをリアルタイムに Lambda・Kinesis Data Streams・Data Firehose・OpenSearch Service へ配信1 ロググループに最大 2 つ。別アカウントへは「送信先（Destination）」を介して配信。リアルタイムの集約・転送に使う。
Logs Insights専用クエリ言語で対話的に検索・集計過去ログのアドホック分析。メトリクスフィルターと違い遡って調べられる。
Live Tailログをリアルタイムにストリーミング表示デプロイ直後の動作確認、障害対応中の監視。
S3 へのエクスポートCreateExportTask でバッチ出力リアルタイムではない（完了まで時間がかかる）。継続的に S3 へ送るなら Firehose へのサブスクリプション。
Contributor Insightsログから「上位の寄与者」（IP、URL など）をランキング特定 IP からの大量アクセス、エラーを多く出すリソースの特定。
データ保護ポリシーログ中の個人情報・認証情報を自動検出してマスク機微データがログに残る問題への対処。閲覧には特別な権限が必要。
KMS 暗号化ロググループをカスタマーマネージドキーで暗号化キーポリシーで logs.<region>.amazonaws.com を許可しないと関連付けに失敗する。
ログクラスStandard と Infrequent AccessIA は取り込み単価が安いが、サブスクリプションやメトリクスフィルターなど一部機能が使えない。

Logs Insights クエリの例

# 直近のエラーを 5 分ごとに集計
fields @timestamp, @message
| filter @message like /ERROR/
| stats count(*) as errors by bin(5m)
| sort errors desc

# Lambda の遅い呼び出し上位 10 件（REPORT 行から抽出）
filter @type = "REPORT"
| fields @requestId, @duration, @maxMemoryUsed
| sort @duration desc
| limit 10
試験の着眼点：どの機能を選ぶか
  • 「特定のエラーが一定数を超えたら通知」→ メトリクスフィルター＋アラーム＋SNS。
  • 「複数アカウントのログを中央のアカウントにほぼリアルタイムで集約」→ サブスクリプションフィルター＋送信先（Kinesis／Firehose）、または CloudWatch のクロスアカウント機能。
  • 「過去 1 週間のログから原因を調べたい」→ Logs Insights（メトリクスフィルターは遡れない）。
  • 「長期保管を安く」→ Firehose 経由で S3 に送り、S3 ライフサイクルで Glacier へ。

CloudWatch エージェント（EC2・ECS・EKS） 1.1.2

エージェントは「インストールしただけでは何も送らない」点が最大の要点です。何を集めてどこへ送るかを書いた設定ファイル（JSON）を作り、その設定を読み込ませて起動する必要があります。

  1. IAM ロールを付ける

    インスタンスプロファイルに CloudWatchAgentServerPolicy（メトリクスとログの書き込み）を付与。Systems Manager で管理するなら AmazonSSMManagedInstanceCore も。設定を Parameter Store に保存する管理用インスタンスには CloudWatchAgentAdminPolicy。

  2. インストールする

    Systems Manager Run Command の AWS-ConfigureAWSPackage（パッケージ名 AmazonCloudWatchAgent）で一括導入するのが運用的。パッケージマネージャーでも可。

  3. 設定ファイルを作る

    ウィザード amazon-cloudwatch-agent-config-wizard か手書き。Parameter Store（例 AmazonCloudWatch-linux）に保存すると全インスタンスで同じ設定を共有できる。

  4. 設定を読み込んで起動する

    amazon-cloudwatch-agent-ctl -a fetch-config -m ec2 -s -c ssm:AmazonCloudWatch-linux（ローカルファイルなら -c file:/path/config.json）。Run Command の AmazonCloudWatch-ManageAgent でも実行可能。

  5. 設定を維持する

    State Manager の関連付け（Association）で定期的に再適用すると、新しく起動したインスタンスにも自動で反映される。

AWS CloudTrail：API の監査証跡 1.1.1 4.1.2

CloudTrail は「誰が・いつ・どこから・どの API を呼び、成功したか」を記録します。設定変更の「中身」を追う AWS Config とは役割が違う点を最初に区別してください。

イベントの種類内容既定の扱い
管理イベントリソースの作成・変更・削除などコントロールプレーンの操作（RunInstances、CreateBucket など）。読み取り／書き込みで分けられるイベント履歴で 90 日間無料で閲覧可能（証跡がなくても）
データイベントリソース内部の大量操作（S3 の GetObject/PutObject、Lambda の Invoke、DynamoDB の項目操作など）記録されない。証跡またはイベントデータストアで明示的に有効化（追加料金）
Insights イベント書き込み API の呼び出し回数やエラー率の異常な増加を検知無効。証跡で有効化
ネットワークアクティビティイベントVPC エンドポイント経由の API 呼び出し（拒否されたものを含む）無効。データ境界の監査に使う
証跡（Trail）
イベントを S3 バケット（任意で CloudWatch Logs にも）へ継続的に配信します。全リージョン対象にするのが推奨。Organizations の管理アカウントから組織の証跡を作ると全メンバーアカウントを一括記録でき、メンバー側では削除できません。
ログファイルの整合性検証
有効化すると 1 時間ごとに SHA-256 のダイジェストファイルが作られ、aws cloudtrail validate-logs でログの改ざん・削除を検出できます。監査要件では必須。
暗号化
既定は SSE-S3。SSE-KMS にする場合はキーポリシーで CloudTrail に暗号化を許可します。
CloudWatch Logs 連携
証跡を CloudWatch Logs に送り、メトリクスフィルター＋アラームで「ルートユーザーのログイン」「セキュリティグループの変更」「認可失敗の多発」などを検知します（CIS ベンチマークの定番）。
CloudTrail Lake
イベントをイベントデータストアに取り込み、SQL で長期間のイベントを横断検索できるマネージドなデータレイク。
配信遅延
API 呼び出しから S3 へのログ配信は通常 5 分程度（保証ではない）。即時の自動対応は EventBridge で受けます。
ひっかけ注意
  • 「誰がセキュリティグループを変更したか」→ CloudTrail。「セキュリティグループのルールが過去どう変わってきたか、ポリシーに準拠しているか」→ Config。
  • EventBridge で AWS API Call via CloudTrail 型のイベントを受けるには、CloudTrail の証跡が有効でなければなりません。
  • S3 のオブジェクト単位のアクセス（誰がファイルを読んだか）はデータイベントを有効化しないと残りません。S3 サーバーアクセスログという別の仕組みもあります。

Amazon SNS による通知 1.1.5

SNS はトピックに発行されたメッセージを、購読（サブスクリプション）している全員に配信する Pub/Sub サービスです。CloudWatch アラーム、S3 イベント通知、EventBridge、AWS Backup、Config、CloudFormation のスタックイベントなど多くのサービスが SNS へ通知できます。

プロトコル
Email／Email-JSON、HTTP/HTTPS、SQS、Lambda、SMS、モバイルプッシュ、Data Firehose。メールと HTTP は購読の確認が完了するまで配信されません。
アクセスポリシー
他サービスがトピックに発行するには、トピックのリソースポリシーでそのサービスプリンシパル（例 s3.amazonaws.com、events.amazonaws.com）に sns:Publish を許可します。aws:SourceArn・aws:SourceAccount 条件で送信元を絞るのが安全。
暗号化
SSE を有効にしたトピックへ AWS サービスが発行するには、カスタマーマネージドキーのキーポリシーでそのサービスに kms:GenerateDataKey* と kms:Decrypt を許可します。
フィルターポリシー
サブスクリプションごとに、メッセージ属性や本文の内容で受け取るメッセージを絞れます。1 トピックを用途別に使い分けられる。
ファンアウト
1 つのトピックに複数の SQS キューを購読させ、同じイベントを並行処理する定番パターン。
配信失敗
サブスクリプションに SQS のデッドレターキューを設定可能。配信ステータスのログを CloudWatch Logs に出して原因を調べられます。

ルールが発火しない・ターゲットが動かないときの調査

  1. ルールは有効か、正しいバス・リージョンか

    AWS サービスのイベントは発生リージョンの既定バスに届きます。カスタムバスにルールを作っても AWS のイベントは来ません。IAM など一部グローバルサービスの API イベントは us-east-1 に届きます。

  2. パターンが実際のイベントと一致しているか

    コンソールの「イベントパターンをテスト」やサンドボックスで、実際のイベント JSON と照合。大文字小文字、配列で書いているか、数値と文字列の型の違い。

  3. メトリクスで段階を切り分ける

    MatchedEvents（一致したか）→ Invocations（呼び出したか）→ FailedInvocations（失敗したか）→ InvocationsSentToDlq。

  4. ターゲット側の権限

    Lambda・SNS・SQS はターゲット側のリソースポリシーで events.amazonaws.com を許可。Step Functions・SSM Automation・Kinesis・ECS タスクなどは EventBridge が引き受ける IAM ロールが必要。暗号化された SQS／SNS はキーポリシーも確認。

  5. 入力の形

    入力トランスフォーマーの出力がターゲットの期待する形式か（JSON として不正だと失敗）。

インスタンスタイプを変更する手順

  1. 互換性を確認する

    同じアーキテクチャ（x86_64／arm64）か、仮想化タイプ（HVM）、ENA ドライバー・NVMe ドライバーの有無、アタッチできる EBS ボリューム数とネットワークインターフェイス数。

  2. EBS-backed なら停止する

    実行中のままタイプは変えられません。インスタンスストアがルートのインスタンスはタイプ変更できないので、新しいインスタンスへ移行します。

  3. タイプを変更して起動する

    停止中にインスタンスタイプを変更して起動。パブリック IPv4 アドレス（Elastic IP でないもの）は変わります。インスタンスストアのデータは消えます。

  4. Auto Scaling 配下なら起動テンプレートを更新

    個々のインスタンスではなく、起動テンプレートの新バージョンを作り、インスタンスの更新（Instance Refresh）で順次置き換えます。

S3 のパフォーマンス戦略とデータ転送 1.3.3

S3 はプレフィックスごとに 1 秒あたり PUT/COPY/POST/DELETE 3,500 件、GET/HEAD 5,500 件を処理でき、プレフィックスを分ければ並列にスケールします。性能の改善策は「アップロードを速くする」「ダウンロードを速くする」「大量データを移す」「保存コストを下げる」の 4 つに分けて覚えます。

課題手段要点
大きなファイルのアップロードマルチパートアップロード100 MB を超えたら推奨、5 GB を超える単一 PUT は不可なので必須。パート（5 MiB〜5 GiB、最大 10,000 個）を並列送信し、失敗したパートだけ再送できる。未完了のアップロードはパートが残り課金されるため、ライフサイクルルールで「不完全なマルチパートアップロードの中止」を設定。

大きなファイルのダウンロードバイト範囲の取得（Range GET）範囲を分けて並列に GET。失敗した範囲だけ再取得できる。

マネージドデータベースのスケーリング 2.1.3

Amazon RDS
RDS のスケール手段
  • 垂直：インスタンスクラスの変更（ダウンタイムあり。マルチ AZ ならスタンバイを先に変更してフェイルオーバーするため短い）。
  • 読み取り：リードレプリカ（非同期レプリケーション。別リージョンも可。昇格して独立 DB にできる）。
  • ストレージ：ストレージの自動スケーリング。空きが 10% 未満の状態が 5 分続き、前回変更から 6 時間経過していると、設定した上限まで自動拡張。
Amazon Aurora
Aurora のスケール手段
  • 最大 15 台の Aurora レプリカ。リーダーエンドポイントで読み取りを分散。
  • Aurora Auto Scaling：レプリカ数をターゲット追跡で増減。メトリクスはリーダーの平均 CPU（RDSReaderAverageCPUUtilization）か平均接続数（RDSReaderAverageDatabaseConnections）。ライターは計算に含まれない。
  • ストレージは自動で拡張（容量の事前確保は不要）。
  • Aurora Serverless v2：ACU（Aurora キャパシティユニット）単位で秒単位に伸縮。プロビジョンドのインスタンスと同じクラスターに混在できる。
演習 PDF の論点（問題 13）

接続数 1,200 で性能が落ちる Aurora → Aurora Auto Scaling のターゲット値を1,000（性能劣化の手前）にする。新しいレプリカが使えるようになるまで数分かかるため、限界値そのもの（1,200）をターゲットにすると間に合いません。レプリカの昇格はフェイルオーバーの仕組みでスケーリングではありません。

ターゲットが Unhealthy になる原因

    ヘルスチェックパスが存在し、Matcher のコードを返しているか（リダイレクトや認証で 301/302/401 になっていないか）。

AWS Backup とスナップショットの自動化 2.3.1

ライフサイクル
N 日後にコールドストレージへ移行、M 日後に削除。コールドストレージは最低 90 日保持が必要なので、削除日は「移行日＋90 日」以上。コールドに対応するリソースは EFS、DynamoDB（高度な機能）、EBS、S3 などに限られる。

論理的にエアギャップされたボールト

組織での一元管理

Data Lifecycle Manager との違い
DLM は EBS スナップショットと EBS-backed AMI 専用でシンプル。複数サービスをまとめ、監査・クロスアカウントコピー・ロックまで必要なら AWS Backup。
演習 PDF の論点（問題 16）
  • 「24 時間ごと・1 年後にコールドストレージ・暗号化」→ カスタマーマネージドキーで暗号化したボールトを作成し、日次ルールとライフサイクル（365 日でコールド）を持つバックアッププランに DynamoDB テーブルを割り当てる。スケジュールやライフサイクルはボールトではなくプランの設定です。
  • DynamoDB の PITR は過去 35 日以内の任意時点への復元で、日次スケジュールやコールド移行の機能はありません。
  • AWS Backup から DynamoDB を復元すると、Auto Scaling ポリシー、タグ、IAM ポリシー、CloudWatch アラーム、TTL、ストリーム設定は復元されないので、IaC やスクリプトで再適用する準備をしておきます。

RPO（目標復旧時点）は「どこまで遡ってデータを失ってよいか」、RTO（目標復旧時間）は「どれだけの時間で復旧すべきか」です。復元方法は、この 2 つとコストの兼ね合いで選びます。

AMI とコンテナイメージの管理（EC2 Image Builder） 3.1.1

AMI はリージョン単位
別リージョンで使うには copy-image でコピー。暗号化された AMI のコピーでは送信先リージョンの KMS キーで再暗号化する。
共有
起動許可でアカウントや組織・OU に共有。AWS マネージドキー（aws/ebs）で暗号化された AMI は共有できない → カスタマーマネージドキーで再暗号化し、キーポリシーで相手アカウントに使用を許可。
作成時の整合性
create-image は既定でインスタンスを再起動して整合性を保つ。--no-reboot は停止しないがファイルシステムの整合性は保証されない。
ライフサイクル
非推奨（deprecation）日時の設定、登録解除の保護、AMI のごみ箱、DLM の AMI ポリシーで古い AMI を自動整理。AMI の公開共有をブロックする設定もある。
最新 AMI の参照
Parameter Store のパブリックパラメータ（例 /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64）を CloudFormation の AWS::SSM::Parameter::Value<AWS::EC2::Image::Id> 型パラメータで参照すると、ハードコードを避けられる。

Image Builder と Systems Manager Automation の使い分け：新規にゴールデンイメージの作成パイプラインを作るなら Image Builder、既存の Automation ランブック（AWS-UpdateLinuxAmi など）でパッチ済み AMI を作り ASG まで更新する一連の処理をスクリプトで組むなら Automation です。どちらも「手作業の AMI 作成」より正解になりやすい選択肢です。ビルド用インスタンスのプロファイルには EC2InstanceProfileForImageBuilder と AmazonSSMManagedInstanceCore が必要で、ビルドが失敗する典型は「サブネットからインターネットや SSM に到達できない」「プロファイルの権限不足」です。

ECS のデプロイと障害対応

ローリング更新
minimumHealthyPercent（更新中に維持する最低割合）と maximumPercent（一時的に増やせる上限）で速度と安全性を調整。
デプロイサーキットブレーカー
新しいタスクが起動に失敗し続けると自動で失敗判定し、前の正常なデプロイへロールバック。
ブルー/グリーン
ECS ネイティブのブルー/グリーンデプロイ、または CodeDeploy との連携で新旧タスクセットのトラフィックを切り替え。
タスクが起動しない
イメージ取得失敗（ECR へのネットワーク経路、実行ロールの権限、ECR 用 VPC エンドポイント）、メモリ不足（OOM）、ヘルスチェック失敗。停止理由は describe-tasks の stoppedReason で確認。
サブネットの IP 枯渇
Fargate や awsvpc ネットワークモードはタスクごとに ENI（IP）を消費する。EKS の VPC CNI も Pod ごとに IP を使うため、プレフィックス委任や追加 CIDR で対処。

CloudFormation の基礎 3.1.2

テンプレート（YAML/JSON）でリソースを宣言し、スタックという単位で作成・更新・削除します。テンプレートのセクションは Parameters・Mappings・Conditions・Resources（必須）・Outputs・Metadata・Transform です。

AWSTemplateFormatVersion: '2010-09-09'
Parameters:
  Env:
    Type: String
    AllowedValues: [dev, prod]
  LatestAmiId:                      # 最新 AMI をパブリックパラメータから取得
    Type: AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>
    Default: /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64
Conditions:
  IsProd: !Equals [!Ref Env, prod]
Resources:
  DataVolume:
    Type: AWS::EC2::Volume
    DeletionPolicy: Snapshot          # スタック削除時にスナップショットを残す
    UpdateReplacePolicy: Snapshot     # 置換が起きるときもスナップショット
    Properties:
      AvailabilityZone: !Select [0, !GetAZs '']
      Size: !If [IsProd, 100, 20]
      VolumeType: gp3
      Encrypted: true
  WebServer:
    Type: AWS::EC2::Instance
    CreationPolicy:                   # cfn-signal を受け取るまで CREATE_COMPLETE にしない
      ResourceSignal: { Count: 1, Timeout: PT15M }
    Metadata:
      AWS::CloudFormation::Init:
        config:
          packages: { yum: { httpd: [] } }
          commands:
            start: { command: systemctl enable --now httpd }
    Properties:
      ImageId: !Ref LatestAmiId
      InstanceType: !If [IsProd, m7i.large, t3.micro]
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash
          dnf install -y aws-cfn-bootstrap
          /opt/aws/bin/cfn-init -v --stack ${AWS::StackName} --resource WebServer --region ${AWS::Region}
          /opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackName} --resource WebServer --region ${AWS::Region}
Outputs:
  VolumeId:
    Value: !Ref DataVolume
    Export: { Name: !Sub '${AWS::StackName}-VolumeId' }   # 他スタックから ImportValue で参照
組み込み関数・機能役割
!Refパラメータの値、またはリソースの主識別子（多くは ID や名前）を返す
!GetAttリソースの属性（ARN、DNS 名など）を返す
!Sub / !Join文字列の組み立て。${AWS::Region} などの擬似パラメータも埋め込める
!FindInMapMappings から値を引く（リージョン別の設定など）
!If / !Equals / Conditions環境ごとの作り分け
!ImportValue他スタックが Export した値を参照（クロススタック参照）
!GetAZs / !Select / !CidrAZ 一覧の取得、リスト要素の選択、サブネット CIDR の計算
動的参照{{resolve:ssm:/path}}、{{resolve:secretsmanager:id:SecretString:password}} でテンプレートに秘密情報を書かずに参照
擬似パラメータAWS::Region・AWS::AccountId・AWS::StackName・AWS::NoValue など

ブートストラップと待機の仕組み

cfn-init
AWS::CloudFormation::Init メタデータに書いたパッケージ・ファイル・コマンド・サービスを適用。
cfn-signal
初期化の成否を CloudFormation に通知。CreationPolicy（または WaitCondition）と組み合わせ、アプリの準備完了まで CREATE_COMPLETE にしない。タイムアウトまでシグナルが来なければ失敗してロールバック。
cfn-hup
メタデータの変更を検知して cfn-init を再実行する常駐デーモン。スタック更新をインスタンス内の設定に反映。
UpdatePolicy
ASG を更新するときの方式：AutoScalingRollingUpdate（バッチで置き換え）、AutoScalingReplacingUpdate（新しい ASG を作って切り替え）。
DependsOn
参照関係がないリソース間に作成順序を明示（例：IGW のアタッチ後にルートを作成）。

スタックの分割

親子関係
ネストされたスタック

親テンプレートの AWS::CloudFormation::Stack で子テンプレートを呼び出す。共通部品（VPC、ALB など）の再利用。親から一括で更新・削除されるライフサイクルの一体性がある。

独立した参照
クロススタック参照

Outputs の Export と !ImportValue。ネットワークチームとアプリチームのように独立して管理するスタック間で値を共有。参照されている Export は変更・削除できないため、参照側を先に変更する。

変更セット・ドリフト検出・保護機能 3.1.2

機能目的要点
変更セット（Change Set）更新を実行する前に、何が追加・変更・置換（Replacement）・削除されるかを確認本番更新の前に必ず作る。置換は「新しいリソースを作って古いものを消す」なのでデータを失う可能性がある（RDS のエンジン変更など）
ドリフト検出コンソールや CLI で手動変更され、テンプレートと実リソースがずれていないか検出状態は IN_SYNC・MODIFIED・DELETED・NOT_CHECKED。検出するだけで自動修正はしない（テンプレートを直すか、リソースを戻す）
スタックポリシースタック更新で特定のリソースが変更・置換されるのを防ぐ JSON ポリシー一度設定すると既定で全リソースが保護される。更新時に一時的なポリシーで上書き可能
削除保護（Termination Protection）スタックの誤削除を防ぐネストされたスタックでは親の設定に従う
DeletionPolicyスタック削除時やリソース削除時の扱いDelete（既定）・Retain（残す）・RetainExceptOnCreate・Snapshot（EBS・RDS・ElastiCache・Redshift など対応リソースのみ）
UpdateReplacePolicy更新で置換が起きたときの旧リソースの扱いDeletionPolicy と同じ値。データを持つリソースには両方指定するのが安全
ロールバックトリガー作成・更新中や直後に指定した CloudWatch アラームが ALARM になったら自動でロールバック監視期間（0〜180 分）を設定
IaC ジェネレーター／リソースのインポート手作業で作った既存リソースをテンプレート化・スタックへ取り込むインポート対象には DeletionPolicy の指定が必要
CloudFormation Hooks／Guardデプロイ前にテンプレートやリソース設定を検査し、ポリシー違反を止めるプロアクティブなコンプライアンス（Control Tower のプロアクティブコントロールもこれ）
ハンズオン（リポジトリ Week 2）

ToDo アプリのスタックで、DynamoDB テーブルの読み書き設定を変える変更セットを作り、内容を確認してから実行します。次にコンソールでテーブルのタグを手で変更し、ドリフト検出で MODIFIED になることを確かめます。テンプレート保存時には cfn-lint iac/cloudformation/wk2-*.yaml を実行し、最後に aws cloudformation delete-stack で削除します。

デプロイ失敗の特定と修復 3.1.3

症状・エラー原因対処
CREATE_FAILED：API: ... is not authorized / AccessDeniedスタックを実行する IAM（またはサービスロール）の権限不足。iam:PassRole の不足、SCP による拒否、KMS キーポリシーイベントタブでリソースごとの理由を確認。サービスロールに必要な権限を追加。CloudTrail で拒否された API を特定
Requires capabilities: [CAPABILITY_NAMED_IAM]IAM リソースを作るテンプレートで承認が未指定--capabilities CAPABILITY_IAM（名前付きなら CAPABILITY_NAMED_IAM、マクロ展開は CAPABILITY_AUTO_EXPAND）
... already exists名前を固定したリソース（S3 バケット名、IAM ロール名など）が既に存在名前を指定せず自動生成させる、または既存リソースをインポート
LimitExceeded / クォータ超過VPC 数、Elastic IP 数などの上限Service Quotas で引き上げ申請、不要リソースの削除
サブネットで IP が足りないサブネットが小さすぎる。AWS は各サブネットで 5 つの IP を予約（/28 なら使えるのは 11 個）大きなサブネット、CIDR の追加。作成済みサブネットの CIDR は変更できない
カスタムリソースで 1 時間止まるLambda が CloudFormation の署名付き URL へ応答を返していない例外時も必ず応答を返す実装（cfnresponse）。タイムアウト設定
DELETE_FAILED中身が残っている S3 バケット、他スタックが Import している Export、スタック外で作られた依存リソース（手動で追加した ENI など）中身を空にする、参照側スタックを先に変更、依存を外してから再削除。残したいリソースは保持（retain）を指定して削除
No updates are to be performedテンプレートとパラメータに差分がないエラーではない。ドリフトしているなら別途対応
Export ... cannot be updated as it is in use参照中の Export を変更しようとした参照しているスタックを先に変更
試験の着眼点：失敗時の調査を楽にする
  • 作成失敗時に原因を調べたいので、作ったリソースを残したい → --disable-rollback（--on-failure DO_NOTHING）、または「正常にプロビジョニングされたリソースを保持」オプション。
  • テンプレートの構文チェックは aws cloudformation validate-template と cfn-lint（このリポジトリでは保存時に自動実行）。
  • 権限を最小にしたまま利用者にスタック操作をさせたい → サービスロールを CloudFormation に渡し、利用者には iam:PassRole とスタック操作権限だけを与える。

AWS CDK 3.1.2

CDK はプログラミング言語（Python・TypeScript など）でインフラを定義し、CloudFormation テンプレートを生成（synth）してデプロイするフレームワークです。最終的には CloudFormation のスタックになるので、スタックの状態やエラーの考え方はそのまま使えます。

from aws_cdk import App, Stack, RemovalPolicy, Tags, aws_dynamodb as dynamodb
from constructs import Construct


class TodoDataStack(Stack):
    def __init__(self, scope: Construct, construct_id: str, **kwargs) -> None:
        super().__init__(scope, construct_id, **kwargs)
        dynamodb.Table(
            self, "TodoTable",
            partition_key=dynamodb.Attribute(name="id", type=dynamodb.AttributeType.STRING),
            billing_mode=dynamodb.BillingMode.PAY_PER_REQUEST,
            point_in_time_recovery=True,
            removal_policy=RemovalPolicy.DESTROY,  # 学習用。本番は RETAIN
        )
        Tags.of(self).add("Project", "soa-c03-workbook")


app = App()
TodoDataStack(app, "wk2-todo-data", env={"region": "ap-northeast-1"})
app.synth()

複数アカウント・リージョンへのプロビジョニングと共有 3.1.4

self-managed
セルフマネージド権限

管理者アカウントに AWSCloudFormationStackSetAdministrationRole、各対象アカウントに AWSCloudFormationStackSetExecutionRole を自分で作り、信頼関係を設定。Organizations を使わない環境向け。

service-managed
サービスマネージド権限

Organizations と統合し、必要なロールは自動作成。OU を対象にでき、OU に追加された新しいアカウントへ自動展開（アカウントが OU から外れたら自動削除も選択可）。委任管理者アカウントから運用可能。

AWS Resource Access Manager（RAM）

RAM は、リソースをコピーせずに他のアカウントや組織・OU と共有する仕組みです。StackSets が「同じものを各アカウントに作る」のに対し、RAM は「1 つのものを皆で使う」点が違います。

よく共有するリソース何ができるか
VPC のサブネット（VPC 共有）参加アカウントが所有者の VPC のサブネットに自分の EC2 や RDS を起動。ネットワークは一元管理、リソースは各アカウントで管理
Transit Gateway各アカウントの VPC を共通のハブに接続
Route 53 Resolver ルールオンプレミスへの DNS 転送ルールを全 VPC で共用
プレフィックスリスト、IPAM プール許可する CIDR 一覧や IP アドレス空間の共有
License Manager の設定、キャパシティ予約、Aurora DB クラスター（クローン用）などライセンス管理、予約済みキャパシティの共用

組織内で共有するときは、Organizations の管理アカウントで「AWS Organizations との共有を有効化」しておくと、招待の承認なしで共有できます。

Route 53 Resolver とハイブリッド DNS 5.2.1

VPC には Amazon 提供の DNS リゾルバー（Route 53 Resolver）があり、VPC CIDR のベース＋2 のアドレス（例 10.0.0.2）または 169.254.169.253 で利用できます。オンプレミスと名前解決を連携させるには、向きに応じて 2 種類のエンドポイントを使い分けます。

インバウンドの SG
オンプレの DNS サーバーからの TCP／UDP 53 のインバウンドを許可。アウトバウンドは応答を返すため全ポートを許可するのが推奨。
アウトバウンドの SG
転送先 DNS サーバーへの TCP／UDP 53 のアウトバウンドを許可。
転送ルール
ドメインごとに転送先を指定し、VPC に関連付け。RAM で他アカウントの VPC と共有できる。「システムルール」で特定サブドメインだけ Resolver に解決させる例外も作れる。
オンプレ側の設定
AWS のゾーン名（例 example.internal）をインバウンドエンドポイントの IP へ転送する条件付きフォワーダーが必要。
演習 PDF の論点（問題 20）

VPC 設定のトラブルシューティング 5.3.1 5.3.4

インターネットから EC2 につながらない

  1. IGW とルート

    VPC に IGW がアタッチされ、サブネットのルートテーブルに 0.0.0.0/0 → igw- があるか（そのサブネットに関連付いた表か）。

  2. パブリック IP

    インスタンスにパブリック IPv4 か Elastic IP があるか。サブネットの自動割り当て設定、ASG の起動テンプレートの設定。

  3. セキュリティグループ

    インバウンドで送信元とポートを許可しているか。

  4. NACL

    インバウンドの許可と、アウトバウンドのエフェメラルポート。番号順に拒否ルールが先に当たっていないか。

  5. OS とアプリ

    OS のファイアウォール、サービスが起動して該当ポートで待ち受けているか。ここで初めてインスタンス内部を疑う。

プライベートサブネットから外に出られない

  1. プライベート側のルート

    0.0.0.0/0 → nat- があるか（IGW を向けても出られない）。

  2. NAT ゲートウェイの置き場所と状態

    パブリック NAT がパブリックサブネットにあり、そのサブネットのルートが IGW を向いているか。状態が Available か、EIP が付いているか。

  3. NACL と SG

    プライベート・パブリック両サブネットの NACL で、行きと戻り（エフェメラル）を許可しているか。インスタンスの SG のアウトバウンド。

VPC エンドポイント経由のアクセスが失敗する

  1. ゲートウェイ型

    エンドポイントがそのサブネットのルートテーブルに関連付けられているか、同じリージョンのバケットか、エンドポイントポリシーとバケットポリシーで許可しているか。

  2. インターフェイス型

    プライベート DNS が有効か（VPC の DNS 属性も true）、エンドポイントの SG がクライアントからの 443 を許可しているか、エンドポイントポリシー。
